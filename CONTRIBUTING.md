# Contributing to Domain Copilot HR Screening

Thank you for contributing to **Domain Copilot**! This platform utilizes an Agentic Workflow and Retrieval-Augmented Generation (RAG) to automate HR resume screening and answer policy questions.

---

## 1. Architecture Overview
The system strictly enforces Clean Architecture and vertical slice patterns:
- **Backend (.NET 8)**:
  - `Core`: Holds domain entities (`CandidateEvaluation`, `AuditLogEntry`) and interfaces (`IResilientLLMService`, `IGroundedGenerationService`). No external SDK dependencies.
  - `Features`: Vertical slices containing MediatR handlers for Screening, Ingestion, and Chat.
  - `Infrastructure`: External adapters for EF Core, Vector In-Memory Store, Gemini API, and Ollama fallback.
- **Frontend (Angular 17+ Standalone)**:
  - Dark-mode Glassmorphism UI built with modern CSS variables.
  - Distinct views for Recruiter ingestion, Copilot Chat with citations, Screening, and Manager Approval Gates.

---

## 2. Development Setup

### Prerequisites
- .NET 8 SDK
- Node.js (v18+)
- Docker & Docker Compose (or local Ollama instance)

### Running the Stack Locally
1. **Clone the repository and prepare configurations:**
   ```bash
   cp .env.example .env
   ```

2. **Backend API:**
   ```bash
   cd src/DomainCopilot.Api
   dotnet restore
   dotnet run
   ```
   API will listen on `http://localhost:5255` (or `http://localhost:8080` in Docker).

3. **Frontend Application:**
   ```bash
   cd src/DomainCopilot.Web
   npm install
   npm start
   ```
   UI will be available at `http://localhost:4200`.

## 3. Contribution Workflow & Standards

### 3.1 Branching Strategy
Create feature branches from main using descriptive names:
- `feature/issue-<id>-brief-description`
- `fix/issue-<id>-brief-description`
- `docs/issue-<id>-brief-description`

### 3.2 Commit Conventions
We enforce the Conventional Commits specification:
- **feat**: A new feature or capability.
- **fix**: A bug fix.
- **docs**: Documentation-only changes.
- **test**: Adding or updating test suites.
- **chore**: Maintenance, configuration, or build tasks.

### 3.3 Pull Request Requirements
- Every PR must address an existing GitHub Issue and reference it in the body (`Closes #<issue_number>`).
- Complete the PR checklist generated by the template (`.github/pull_request_template.md`).
- Ensure no real secrets or API keys are committed.

---

## 4. Quality Gates & Testing Standards

Before opening a PR, all changes must pass the following local quality checks:

**Unit & Integration Tests:**
```bash
dotnet test
```

**Agentic RAG & Refusal Evaluation (FR-3 Gate):**
```bash
cd eval
npm run eval:qa
```
- Must maintain $\ge 90\%$ Retrieval Hit-Rate and $100\%$ Refusal Correctness on adversarial queries.
- **Clean Architecture Check**: Ensure domain entities in Core do not import external infrastructure libraries.
